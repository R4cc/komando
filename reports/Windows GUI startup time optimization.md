# Create the real GPU device first, win 39 ms

Komando's warm launch is gated by a single cost it cannot shrink, only hide: the NVIDIA user-mode driver spends about **116–120 ms inside `D3D11CreateDevice`**. The existing background "warm-up" hides little of it, because it calls `D3D11CreateDevice` with `ppDevice = NULL` (a support check) and never builds a device. The technique to ship first is Prototype A: create gpui's real `DirectXDevices` on a background thread at platform creation (~10.5 ms after process start) and join it in `attach_gpu`. In first-party measurements on 2026-11-27 this cut the first painted frame from **232 to 193 ms**, and the README harness's CreateProcess-to-visible median from **201.8 to 162.6 ms (−39 ms, −19%)**, with nothing visible changing. The second change, `GetSystemFontCollection(checkForUpdates=false)`, cuts DirectWrite setup from **52 ms to 1.6 ms** but adds nothing on this RTX 5070 Ti once A lands. It is still worth merging: it is a one-line change that Zed upstreamed after measuring 90 ms off the first frame on a Ryzen laptop, and it becomes the critical path wherever device creation is faster or the font cache is cold. The next step is to move about 20 ms of app work (highlight-regex compile, embedded-font registration, component library) into the ~50 ms the main thread now spends waiting for the device. That is estimated, not prototyped. Showing the window only after its first Present removes a 35 ms empty-window state but moves the "visible" timestamp later, so it is polish rather than a speedup. Process-level levers (delay-loading, PGO, prefetch, signing) and device-creation flags offer nothing measurable on a warm launch that reaches `main` in 10.5 ms. Together, A, B and the idle-time work project to a first frame near **173 ms, about 25% below today**. Everything beyond A is either measured on one machine or estimated.

## The NVIDIA driver owns half of a 232 ms launch

The baseline main-thread timeline (first-party, warm, medians of 8–10 runs, Ryzen 7 9800X3D, RTX 5070 Ti, Windows 11 build 26300) has two big synchronous blocks. Everything else is small:

| Milestone (ms since process creation) | Baseline | B alone | Prototype A | A + B |
|---|---:|---:|---:|---:|
| `main` reached | 10.5 | 10.5 | 10.5 | 10.5 |
| DirectWrite setup | 11.5→63.7 (52 ms) | 1.6 ms | 11.5→63.7 | 1.6 ms |
| Hidden platform window + drag-drop helper done | 78 | — | 78 | ~27 |
| GPU devices ready | 170 (`DirectXDevices::new` 79→170) | — | 130 (background) | 130 |
| Window shown | 197–198 | — | 159 | — |
| First painted frame | 232 | 226 | 193.8 | 192.6 |
| Harness: CreateProcess→visible (10 launches) | 201.8 (199–219) | — | 162.6 (154–187) | — |

Everything after the device is small. Swap chain, pipelines and DirectComposition together take about **4 ms** (179→182). The Komando workspace build takes 8 ms, highlight-rule regex compilation 12 ms and first layout 9 ms. The device itself is the outlier. External measurements put it in the same range on every discrete GPU tested. On an RTX 3090, `D3D11CreateDevice` took **159.6 ms of a 184.2 ms startup (87%)**, against 3.6 ms for WARP on CI ([nene-nib #24](https://github.com/hideyukiMORI/nene-nib/issues/24)). On an RTX 5070 under the same Windows build 26300, the first creation took **96.6 ms** and later re-creations 74.8–76.5 ms. The reporter concluded that "nearly all of the reopen is creating the device itself", not the swap chain or surfaces ([expo/exact #1195](https://github.com/expo/exact/issues/1195)). AMD is cheaper but not free: **55–71 ms** on a desktop Radeon behind a GPUI fork ([Lodestone PR #761](https://github.com/Lodestone-Team/lodestone/pull/761)), **115–150 ms** on a Radeon 680M iGPU ([amigo-blinzel PR #8](https://github.com/amigo-labs/amigo-blinzel/pull/8)).

The warm-up fails for a reason these sources predict. With the warm-up disabled, devices take **116–120 ms from scratch** (74→190, first frame 256). With it, they still take **91 ms**. So the support check pre-pays only about 25–29 ms, the one-time share (DLL mapping, driver-global initialization), and leaves the per-device initialization untouched. That matches the ~20 ms first-versus-later gap on the RTX 5070 ([expo/exact #1195](https://github.com/expo/exact/issues/1195)). It also matches nene-nib's finding that a second device in the same process costs the same as the first (**159.5 vs 159.0 ms**), "a fixed driver cost paid on every call" ([nene-nib PR #29](https://github.com/hideyukiMORI/nene-nib/pull/29)). A warm-up can never fix that, whether it builds a device or not. Only the real device, started early, removes the cost from the critical path.

## Building the real device on a worker cuts 39 ms with no visible change

Prototype A starts gpui's real `DirectXDevices` on a background thread at platform creation, deletes the warm-up, and joins in `attach_gpu`. The devices become ready at **130 ms**. That is about 120 ms after the thread starts, the full from-scratch cost, so the whole saving comes from overlap: the device is now built while DirectWrite and the platform window are set up. First frame drops **232→193 ms**, window shown **197→159 ms**, and the independent startup harness confirms **−39 ms / −19%** at the median. The tail tightens too (worst run 219 → 187 ms).

Two external projects reached the same result by the same route. Lodestone's GPUI fork moved DirectX device creation ahead of OLE, DirectWrite and platform-window setup, with `attach_gpu` waiting for it. Median first frame went **244.5→213.1 ms**, or **160.2→123.8 ms** on top of another change. `attach_gpu` still waited about 20 ms, because the main thread had only ~40 ms of other work ([Lodestone PR #761](https://github.com/Lodestone-Team/lodestone/pull/761), [fork commit](https://github.com/Lodestone-Team/zed/commit/39a9cfcfd2d65b31b28915bc543d3fdf76491e80)). nene-nib's NVIDIA handoff saved a smaller **15 ms** (194.9→179.9 ms), because its UI thread had less work to overlap. Creation on the worker ran 4–5 ms slower than on the UI thread ([nene-nib #481](https://github.com/hideyukiMORI/nene-nib/issues/481)). Komando sits between the two: about 68 ms of main-thread work (10.5→78) runs in parallel with the device.

The pattern is within Direct3D's documented contract. Microsoft states that "the use of a Direct3D 11 device (ID3D11Device) is thread-safe". The immediate context is not, and the thread that owns it "should also use that same thread for … IDXGISwapChain::Present" ([Microsoft Learn: Multithreading in Direct3D 11](https://learn.microsoft.com/en-us/windows/win32/direct3d11/overviews-direct3d-11-render-multi-thread-intro)). Handing the device over once through the join is safe, as long as the swap chain and all immediate-context work stay on the main thread. `D3D11_CREATE_DEVICE_SINGLETHREADED` must stay unset, because it voids the thread-safety guarantee ("undefined behavior") ([D3D11_CREATE_DEVICE_FLAG](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ne-d3d11-d3d11_create_device_flag)). Lodestone's safeguards are worth copying. Create the device exactly once. Recreate it on the main thread only if the background attempt fails or panics. Leave device-lost recovery unchanged. The one side effect is that the worker is busy for ~120 ms, so other background tasks queued at startup should not share it ([nene-nib #481](https://github.com/hideyukiMORI/nene-nib/issues/481)).

One cheap experiment remains. amigo-blinzel saw `D3D11CreateDevice` drop from **~150 to ~95 ms** when its UI thread pumped messages instead of blocking ([amigo-blinzel PR #8](https://github.com/amigo-labs/amigo-blinzel/pull/8)). That is a single unexplained anecdote. Under A, the background creation already costs the same ~120 ms as an unblocked from-scratch creation, so the blocking join does not appear to inflate it. Still, an hour spent pumping messages during the join, instead of blocking, would settle the question. **Verdict: implement A now.** It is the largest measured win, it changes nothing the user sees, and two GPUI forks have used the same pattern.

## One DirectWrite flag saves 50 ms, just not on this GPU

`DirectWriteTextSystem::new` calls `GetSystemFontCollection` with `checkForUpdates=true`. Microsoft defines this as "an immediate check for changes to the set of system fonts". With `false`, the function "will still detect changes if the font cache service is running, but there may be some latency" ([IDWriteFactory3::GetSystemFontCollection](https://learn.microsoft.com/en-us/windows/win32/api/dwrite_3/nf-dwrite_3-idwritefactory3-getsystemfontcollection)). Prototype B flips the flag. DirectWrite setup falls **52 ms → 1.6 ms**, yet the first frame moves only **232→226 ms** on its own, and with A it moves nothing (**193.8 vs 192.6 ms**). The likely reason for both: the device chain is the critical path. On its own, B lets the main thread reach `DirectXDevices::new` while the support-check warm-up (finished at ~75 ms) is still running, so the real device gains little. Under A, B only lengthens the main thread's idle wait, from 79→130 to 27→130. That is an inference from the timeline, not a traced result.

The flag matters as soon as the device stops being the bottleneck. Zed merged the same change upstream on 2026-11-24 after measuring the DirectWrite font collection at **72.5→1.34 ms**, GPUI initialization at **143.8→57.8 ms** and the first painted frame at **285.3→195.6 ms**. Those numbers come from a Ryzen 5 PRO 5650U with 137 font families and 50 fresh processes per variant ([zed-industries/zed#66001](https://github.com/zed-industries/zed/pull/66001)). Under A on a desktop AMD GPU, where devices take 55–71 ms ([Lodestone PR #761](https://github.com/Lodestone-Team/lodestone/pull/761)), the device would be ready around 65–80 ms. The 52 ms DirectWrite block plus the platform window, ending at 78 ms, would then be the critical path. Cold or broken font caches widen the gap further: Mozilla recorded a Windows 10 user whose `GetSystemFontCollection` took **over 1 s**, against 2 ms on a developer machine, and suspected a cache rebuilt on every launch ([Mozilla bug 1766908](https://bugzilla.mozilla.org/show_bug.cgi?id=1766908)).

The trade-off is narrow. A font installed seconds before launch can be missing from the collection for a moment. A lookup that misses still forces a refresh in `select_and_cache_font`. The font list (`all_font_names`, which feeds the font picker) can omit a just-installed font until that refresh. Adding a forced check on the first `all_font_names` call would bring the synchronous rebuild back, because the app lists fonts while resolving its theme ([Finityno/zed PR #81](https://github.com/Finityno/zed/pull/81)). **Verdict: implement B** as cheap insurance for non-NVIDIA and cold-cache machines. Expect no gain on the reference machine, and pick it up through the upstream gpui change if Komando tracks it.

## Fifty idle milliseconds can absorb roughly 20 ms more

After A, the main thread finishes platform setup at 78 ms and then waits until 130 ms for the device. With B, it waits from about 27 ms. Meanwhile, the work after the device (130→193 ms) still includes app work that does not need a GPU: embedded-font registration (6 ms), component library setup (2 ms), highlight-rule regex compilation (12 ms) and settings/library loading (<1 ms). Moving it into the wait, or onto another thread, should save **about 20 ms**. That estimate comes from the measured durations and has not been prototyped. It mirrors the ~20 ms Lodestone left on the table in `attach_gpu` ([Lodestone PR #761](https://github.com/Lodestone-Team/lodestone/pull/761)).

The simplest form needs no new threads. The wait (51 ms, or ~103 ms with B) is larger than all the movable work combined, so the main thread can do that work before it joins the device. The only obstacle is init order: Komando code has to run before gpui reaches `attach_gpu`, which needs a hook or a reordering in the fork. Running the work on the main thread also sidesteps an open question. Microsoft documents no thread-safety guarantee for `IDWriteFactory` or `IDWriteFontSetBuilder`, and even the piet-direct2d authors note they "couldn't find any documentation about using IDWriteFactory in a multi-threaded context" ([piet-direct2d dwrite.rs](https://docs.rs/piet-direct2d/0.6.1/src/piet_direct2d/dwrite.rs.html)). If the regex compile moves to a worker instead, it needs settings first (<1 ms) and a join before first layout.

Font registration has one more small lever. DirectWrite copies an in-memory font buffer unless the caller passes an owner object. Adding all embedded fonts to one builder in a single pass avoids building an empty set and rebuilding it later ([Microsoft Learn: Custom Font Sets](https://learn.microsoft.com/en-us/windows/win32/DirectWrite/custom-font-sets-win10)). Each would shave part of the 6 ms, and under A that time is already hidden. **Verdict: worth doing after A**, measured item by item, starting with the 12 ms regex compile.

## Showing after the first Present trades a metric for polish

Under A, the window becomes visible at 159 ms and paints at 193 ms, so it sits empty for about 35 ms. With `WS_EX_NOREDIRECTIONBITMAP` there is no redirection surface, and "windows without a compositor surface become invisible". The client area shows nothing until the first DirectComposition commit. For the same reason, the GDI class-brush and GDI-fill tricks used by Chromium and Firefox cannot work as placeholders here ([Bugzilla 1906358](https://bugzilla.mozilla.org/show_bug.cgi?id=1906358)). The fix that fits Komando is the order Alacritty uses: create the window hidden, clear and present a frame, then show it ([alacritty display/mod.rs](https://raw.githubusercontent.com/alacritty/alacritty/master/alacritty/src/display/mod.rs)). Zed's open PR #63134 does the same in GPUI. It applies placement while the window is hidden, presents the first frame and shows the window from `PlatformWindow::draw`. That "keeps the OS window-open animation, lays the first frame out at the final position, size and DPI … and never shows a frame without content" ([zed-industries/zed#63134](https://github.com/zed-industries/zed/pull/63134)).

The cost is perception and measurement, not time. Windows Terminal's author put it plainly when landing the same change: "This will result in the window seemingly not loading as fast, but it will actually take exactly the same amount of time before it's usable" ([microsoft/terminal#12979](https://github.com/microsoft/terminal/pull/12979)). Komando's harness measures CreateProcess-to-visible, so under A it would report about 193 ms instead of 162.6 ms, which looks like a regression although content arrives no later. The harness should time first frame before this lands. Two pitfalls are documented. Cloaking with `DWMWA_CLOAK` and then uncloaking breaks the open animation ([Bugzilla 1906358](https://bugzilla.mozilla.org/show_bug.cgi?id=1906358)), so delay `ShowWindow` rather than cloak. Applying placement in the wrong place made persisted windows on a secondary monitor shrink on every launch, until the window was created hidden early and only shown late ([microsoft/terminal#13098](https://github.com/microsoft/terminal/pull/13098), [#13811](https://github.com/microsoft/terminal/pull/13811)). Electron also warns that waiting for the first frame can make an app "feel slow" when that frame is late ([Electron BrowserWindow docs](https://www.electronjs.org/docs/latest/api/browser-window)). At 193 ms, Komando's first frame is not late. **Verdict: worth doing as a UX change**, separate from the speed work, with the benchmark redefined first.

## Every other lever fails the warm-launch test

Komando reaches `main` 10.5 ms after process creation. That caps what loader, image-layout and antivirus work can be costing on a warm launch. The device-level alternatives either save nothing or add a visible placeholder state, which breaks the "same user experience" constraint.

| Technique | Expected warm-launch saving | UX side effects | Verdict |
|---|---|---|---|

| **B. `checkForUpdates=false`** | 0 ms here with A; −6 ms alone; −90 ms first frame on Ryzen 5650U ([zed#66001](https://github.com/zed-industries/zed/pull/66001)) | Just-installed font briefly missing from the list | **Implement** |

| Creation flags (SINGLETHREADED, fewer feature levels) | 0 ms (158.2 / 161.8 vs 159.0 ms) ([nene-nib PR #29](https://github.com/hideyukiMORI/nene-nib/pull/29)) | SINGLETHREADED forbids the A handoff | No |

| BOLT | N/A: ELF only ([rust-lang/rust#103595](https://github.com/rust-lang/rust/issues/103595)) | — | No |
| Prefetcher / `/prefetch:N` | Smallest gains "on SSD devices with no load" ([Microsoft](https://learn.microsoft.com/en-us/archive/blogs/chadduffey/what-is-application-launch-prefetching)); Mozilla saw no change ([bug 1878993](https://bugzilla.mozilla.org/show_bug.cgi?id=1878993)) | None | Nothing to do |
| Authenticode signing | ~0 ms warm; Defender scans unsigned binaries on launch ([Microsoft Learn](https://learn.microsoft.com/defender-endpoint/troubleshoot-performance-issues)) | Avoids Smart App Control blocks ([Lawrence](https://textslashplain.com/2026/04/28/smart-app-control/)) | Yes, for first launch after update, not for warm launches |

PGO deserves a word of caution rather than dismissal. Its gains come from faster CPU-bound code. After A, the CPU-bound part of Komando's critical path is the ~60 ms from device-ready to first frame, and a 10–17% gain there is single-digit milliseconds. That projection is extrapolated from Chrome, not measured. Signing belongs on the distribution roadmap: the 10.5 ms to `main` shows Defender already has a cached verdict on the developer machine, but each new unsigned build has to earn it again.

## Conclusion

After A, Komando's startup is a race between two parallel chains: a driver chain (about 120 ms of device creation from 10.5 ms) and a CPU chain (DirectWrite, platform window and app work). Which one wins depends on the machine. On this NVIDIA desktop the driver chain wins by about 50 ms, so B looks worthless. On an AMD desktop the result likely flips, and B becomes the larger lever. The practical consequence is that every remaining optimization needs a second benchmark machine, ideally an Intel or AMD GPU and a post-reboot cold run, before it is judged. A single RTX 5070 Ti hides half the story. The NVIDIA floor is now visible: with the device ready at ~130 ms and nothing in Komando's power to shorten driver initialization, the first frame cannot go much below 130 ms plus whatever post-device work remains. The ~173 ms projection leaves roughly 40 ms of that work to examine.

The cheapest next diagnostic is in the existing timeline. Between the renderer finishing (182 ms) and the window being shown (198 ms) in the baseline, 16 ms are unattributed. That gap, plus the amigo-blinzel hint that message pumping speeds up driver initialization, are the two leads most likely to turn up something no external source has measured. A short WPR trace with stack sampling would resolve both.
